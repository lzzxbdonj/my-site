# ai自学通 · 薄利多销商业化方案（可执行草案）

> 这份文档是**方案与参数化计算**，不是承诺：所有价格都是「示例实验价」，需要你自己用真实账单校准。
> 本仓库**没有**接入任何支付、账号、计费或 Cloudflare 商业部署；下面明确区分「已有能力」与「尚未实现的提案」。

## 1. 一句话思路：用「可审计的复用课」补贴「按需定制课」

薄利多销要成立，先把两件事分开：

1. **可复用的低成本课程（audited reusable）**：由你（或小团队）审核过一次的课程内容，之后所有用户看到的是**同一份**内容。
   - 边际成本接近 0：**复用不会重新调用模型，因此不会产生新的供应商 token 消耗**（缓存/静态内容是服务与维护成本，不是 token 成本）。
   - 定价因此**不应该**声称「按 token 收费」，而应说明「你付的是审核、托管、检索与服务」。
   - 这部分承担「低价走量」的角色：它决定你的获客成本能不能被摊薄。
2. **按需定制课程（metered bespoke）**：用户输入主题、当场调用模型生成。
   - 每次生成都有真实、可变的模型成本（1 次大纲 + N 个知识点 ≈ 1+N 次调用）。
   - 必须**计量 + 预授权上限**，绝不做「无限次终身 AI 生成」这类承诺：一次生成的真实成本取决于主题、模型、输出长度、是否失败重试，无法预先钉死。

组合起来才是薄利多销：**低价可复用课负责量，计量定制课负责毛利**。

> 目前仓库里 AI 建课是**你自己配 Worker + 你自己付供应商费**的模式（BYO Worker）。把它变成商业产品，缺的不是提示词，而是下面的计量、账务与合规层。

## 2. 成本参数表（全部参数化，价格待你填真实值）

把下面每一项都当成**参数**，而不是写死的数字。任何报价前先把这张表填上你自己的真实单价。

| 参数 | 含义 | 计量单位 | 你的取值 | 备注 |
| --- | --- | --- | --- | --- |
| `p_in` | 输入 token 单价 | 元 / 千 tokens | 待填 | 不同模型差异很大 |
| `p_out` | 输出 token 单价 | 元 / 千 tokens | 待填 | 通常显著高于输入 |
| `p_cache_hit`（`p_hit`） | 缓存命中**那部分输入**的单价 | 元 / 千 tokens | 待填 | 只对命中缓存的输入适用；未提供该字段时按 `p_miss` 计 |
| `p_cache_write` | 缓存写入单价 | 元 / 千 tokens | 待填 | 有些供应商单独收费 |
| `model_mix` | 模型分层策略 | — | 待填 | 例如「便宜模型跑大纲/概念课，贵模型跑实验室单元」 |
| `Tin` / `H` / `Tout` | 输入总量 / 其中缓存命中量 / 输出总量 | tokens / 次调用 | 实测 | 从 `usage` 汇总。注意：`prompt_tokens` **通常已经包含**缓存命中部分，因此 `H <= Tin`，不要把 H 再加一遍（见 3.1） |
| `r_fail` | **预估**失败储备系数 | 倍数 | 待填（起步按 1.15-1.3 估） | 只用于**事前**预估；**不能**再和已经观测到的失败调用相加（见 3.1） |
| `c_cf` | Cloudflare Worker 成本 | 元 / 月 | 待填 | 免费额度内为 0，超量按请求数/CPU 计 |
| `c_store` | 存储与备份成本 | 元 / 月 | 待填 | 复用课的静态内容可放 R2/对象存储 |
| `c_queue` | 队列/异步任务成本 | 元 / 次 | 待填 | 长课程异步生成需要 |
| `c_support` | 人工支持成本 | 元 / 单 | 待填 | 客诉、退款、审核争议 |
| `c_acq` | 获客成本 | 元 / 新客 | 待填 | 广告/内容/渠道分成 |
| `f_pay_rate` | 支付手续费率 | % | 待填（常见区间 0.6%-3%） | 以你的实际通道合同为准 |
| `f_pay_fixed` | 支付固定费/最低费 | 元 / 笔 | 待填 | **低价单尤其致命**：固定费会吃掉小额的毛利 |
| `refund_rate` | 退款率 | % | 待填 | 与「先预授权、后结算」策略直接相关 |
| `tax_rate` | 税率与合规成本 | % | 待填 | 视经营主体与地区而定 |

**真实单价必须以你自己的账单为准**：本仓库**没有验证**任何供应商的当前价目表（价格会变，且常有阶梯/缓存/夜间折扣）。历史情况要如实区分：继承的历史里做过**部分真实调用**（大纲 + 前 4 个知识点这类小批量，见 README 的「live-call 历史边界」），但**没有拿到也没有核对过任何准确账单**；本轮 Stage 1 的测试与验收**全部是零付费调用**（本地模拟供应商响应）。

## 3. 计量：先做「内部按 token 记账」，对外只卖信用点

### 3.1 内部实际成本（事后按已观测用量核算，并计入失败的实际支出）

每次生成把**大纲 + 全部知识点**的用量汇总起来（现在产品界面就是这么显示的，见下）：

```
# 逐模型（m）分别算再相加；单价按「元 / 千 tokens」，所以最后要除以 1000
成本_模型(m) = [ (Tin_m - H_m) × p_miss_m + H_m × p_hit_m + Tout_m × p_out_m ] / 1000
             + (缓存写入单独计费时) CacheWrite_m × p_cache_write_m / 1000

成本_单次生成(事后)     = Σ_m 成本_模型(m) + 已实际发生的失败调用成本
成本_单次生成(事前预估) = 同上 × r_fail        # 只用于预估；事后核算不再乘 r_fail
```

要点：

- **`Tin` 是输入总量、`H` 是其中缓存命中的部分（`H <= Tin`）**：`prompt_tokens` 一般已经包含缓存命中，所以缓存那部分要先从 `Tin` 里减掉，再分别用 `p_miss` 与 `p_hit` 计价；**不要把 H 再加一遍**（否则缓存命中会被算两次）。
- **`p_cache_write` 只在供应商明确单独计量缓存写入时才需要**；如果它已包含在输入单价里，就不要再加一项。
- **逐模型累加**：同一门课可以混用便宜模型（大纲/概念课）与贵模型（实验室单元），不能只取一个单价。
- **预估的 `r_fail` 与事后的失败支出不能同时使用**：事后成本里失败调用该多少就多少（供应商可能对无效输出、截断、超时计费）；`r_fail` 只是事前预留系数，重复相加会高估成本。
- **数据来源的诚实边界**：能拿到的 `usage` 只来自**成功响应**；失败与超时通常**不返回 usage**，因此事后汇总很可能**低估**真实支出——这正是需要预留失败储备的原因。严谨核算应另外记录调用次数（尝试数），按其是否可能计费单独估算。

### 3.2 对外报价：不要直接按 token 明码标价

「按 token 价值定价」是个合理方向，但直接把 token 当零售单位有三个坑：

1. **token 数不可预期**：同一主题换个模型、换个长度，成本可能差 3-5 倍；用户无法预判自己会被扣多少。
2. **计价单位会变**：供应商调价、模型换代、缓存策略变化，都会让「1 元 = X token」这种锚点失效；写成公开承诺后就很难改。
3. **缓存命中让 token 与价值脱钩**：复用课几乎不消耗新 token，却仍有审核与服务成本；按 token 卖会让复用课的定价显得莫名其妙。

所以建议：

- **内部**：严格按上面的公式做真实 token 成本核算（用于选模型、算毛利、定信用点单价）。
- **对外**：卖**学习信用点**，并给出**透明且带版本的换算说明**，例如「1 个信用点 ≈ 一次 6 知识点定制课（按我们当前默认模型与输出长度的实测均值估算）」。
  - 换算表要写清**版本号与生效日期**，改动时公示，已购信用点按购买时的版本扣减（不做暗中改价）。
  - 下单前给用户**人民币预估**（区间），而不是只给 token 数。
  - 用户可设**硬性支出上限**（本次/本月最多扣多少信用点/多少钱），到上限即停止，不做「自动续跑直到成功」。
  - 若走商户代收（你自己收钱再转给供应商），要如实说明**是否含商户服务费**以及它在什么条件下收取。

### 3.3 用户善意与预授权：先预留，后结算

- 发起时**预留该次生成的最大信用点/额度**（覆盖 1+N 次调用 + 重试余量）。
- **只对「成功且通过校验的交付」结算**：课程完整拼装并通过结构校验才扣费。
- 未用掉的部分**释放**回用户账户。
- **无效输出的重试由商户自己承担**（这是你的成本，不是用户的），但要在条款里说明「供应商可能已经对失败调用计费，因此这部分由我们吸收」。
- 失败时如实展示已发生的尝试次数与用量（产品现在已经这样做），不承诺「失败不计费」。

## 4. 毛利与定价公式

```
单课收入   = 售价 (P)
单课成本   = 模型成本(c_model) + 基础设施(c_infra) + 支持(c_support) + 获客分摊(c_acq) + 退款与坏账(含在 refund_rate) + 税费(tax) + 支付费(f_pay)
支付费     = P × f_pay_rate + f_pay_fixed            （注意固定费对低价单的影响）
毛利       = P - 单课成本
毛利率     = 毛利 / P
目标条件   = 毛利率 ≥ 目标毛利率(例如 40%-60%，自定义)，且 单课毛利 ≥ f_pay_fixed × 3
```

**低价单的陷阱**：假设 `f_pay_fixed = 0.5 元/笔`，你卖 2 元一单，支付固定费就吃掉 25% 的毛利；再叠加退款、支持与税费，很容易变成负毛利。所以「薄利」不能靠把单价压到接近 0，而要靠：

1. **提高单笔客单**（一次买 10 个信用点，而不是每次付 2 元）；
2. **让大部分请求命中复用课**（边际成本≈0）；
3. **把定制课的最低可行价设在「固定费 + 支持成本 + 税」之上**。

## 6. 已有能力 vs 尚未实现（别把提案当现状）

**已有（本仓库当前真实实现）**

- 静态前端 + 本地 `localStorage` 进度，无账号、无遥测。
- 分阶段建课：`POST /api/course/outline` + `POST /api/course/lesson`（1+N 次尝试）。
- Worker 侧 Durable Object **原子尝试额度**（默认 60/访客/天、200/站/天）与并发上限（默认 2）——这是**防滥用**，**不是鉴权**。
- `ALLOWED_ORIGINS` 的 CORS 白名单——同样**只防浏览器跨站调用，不是身份认证**。
- 服务端按 `CF-Connecting-IP` + `IP_SALT` 做加盐哈希后限流（不存明文 IP）；**IP 不是账号**，同一网络下的用户会互相挤占。
- 前端展示服务端回报的**输入/输出/合计 tokens 与尝试次数**（大纲 + 全部知识点的汇总），并明确「不等于供应商账单的精确金额」。
- 失败续跑（只补未完成知识点）、重复点击去重、换输入即重新开始。
- 课程模板（5 个预设 + 自定义）：降低用户填写成本，但生成仍然消耗真实 token。

**尚未实现（提案，需要单独的设计与实现才能上线）**

- 账号体系与登录（现在的「身份」只是本地浏览器 + 加盐 IP）。
- 服务端信用点/钱包账本（原子扣减、冻结、释放、对账）。
- 支付接入、发票/税务、退款流程。
- 支付回调（webhook）的**幂等**处理与重放防护；订单与生成任务的对账。
- 服务端课程任务持久化（现在的中间进度只在该标签页内存里，刷新即丢）。
- 服务端课程缓存/去重（同需求命中缓存 → 不重复调用模型）。
- 队列与长任务（现在依赖单个请求的超时窗口）。
- 不可变的用量溯源（谁在什么时候、用哪个模型、花了多少 token）与**带版本的价格表**。
- 反作弊：不接受客户端上报的 token 数作为计费依据，一切以服务端观测为准。

### 6.1 【提案 · 尚未实现】注册与验证码（邮箱 OTP + Turnstile）

> 状态：**已实现「GitHub 登录」（方案 A），邮箱 OTP 仍是提案。**
> 已落地部分：`worker/src/auth.js`（签名 state、无状态会话令牌、GitHub 换 token/取用户）、端点 `GET /api/auth/login|callback|me`、设置页的账号面板、前端 `src/core/auth-client.js`；单元与浏览器测试均使用**模拟 GitHub**，不访问外网、不产生任何费用。启用步骤见 [`worker/README.md`](../worker/README.md)。
> 尚未实现：邮箱/短信 OTP、账号与信用点账本、支付。下面关于邮箱 OTP 的内容是**上线前要做成什么样**的设计，不是现状。
> 邮箱服务商与域名**都还没选定**；并且**当前没有自有域名**，这直接影响下面的选型（见「没有域名怎么办」）。
> 本文件**不包含**任何服务商密钥或账号配置。

**趋势与选型（先便宜、后扩量）**

- **初期：邮箱一次性验证码（email OTP）**。相对短信，它的**单位成本通常更低、无需短信资质**，因此在薄利多销阶段更常见——但具体单价与送达率**取决于你签约的服务商、发信域名信誉与收件方策略**，本仓库无法验证，必须按你自己的账号与实测结果衡量（并做**分地区送达测试**，不要把「覆盖各国」当成已经验证的事实）。
- **同时叠加服务端校验的 Turnstile**（人机校验）：它是**独立的反自动化措施**，必须由 Worker 调用站点校验接口验证 token；它**不能**替代账号鉴权，也不能当作「已登录」的凭据。
- **短信 OTP 建议后置**：单价高、需要区域合规与签名/模板报备、不同国家送达差异大；等有明确付费场景和量之后再加，并单独做成本核算（见第 2 节 `c_support`、按地区单列）。

**没有域名怎么办（当前的真实约束）**

要往**任意用户**的邮箱发验证码，实务上**必须有一个可控域名**：邮件服务商要求你在 DNS 里配置 SPF/DKIM（部分还要求 DMARC）来证明发信域归你所有，否则邮件要么发不出去，要么大量进垃圾箱。没有域名时，各服务商通常只允许两种受限用法：

1. **测试模式**：只能发到你自己账号绑定的邮箱（例如 Resend 的 `onboarding@resend.dev` 只能发给你自己的注册邮箱）；
2. **单发件人验证**：验证一个你拥有的**邮箱地址**作为发件人（Brevo、Mailjet 都支持）。技术上能发，但用 `qq.com` / `gmail.com` 这类公共邮箱当发件人，**送达率会明显变差**，很多收件方会直接拒收或进垃圾箱——**不适合作为面向付费用户的正式注册通道**。

因此在不买域名的前提下，推荐顺序是：

- **方案 A（推荐：先不做邮箱 OTP）**：用**第三方登录**（GitHub OAuth，你的受众本来就在 GitHub 上）作为主身份，邮箱只作可选补充。
  - 零域名、零发信成本、没有送达率问题；账号本身即是反自动化门槛。
  - 代价：需要在 Worker 机密里保存 OAuth 的 client secret（符合现有「密钥只在 Worker」的架构）。
- **方案 B（要邮箱 OTP）**：先买一个便宜域名（常见后缀的**年费大致是「一杯咖啡」量级**，具体以注册商报价为准），再配邮件服务：
  - **Resend**：开发者体验最好、集成最简单，免费额度较小（**约 3,000 封/月、100 封/天**），**必须验证域名**。
  - **Brevo**：免费额度偏「每天」计（**约 300 封/天**），支持单发件人验证，便于在没域名时先小范围试跑。
  - **Mailjet**：免费额度偏「每月」计（**约 6,000 封/月、200 封/天**），同样支持单发件人验证。
  - ⚠️ 以上额度与规则**会变**，务必以各家官网**当时的**条款为准；本仓库没有开通、也没有验证过任何一家。
- **方案 C（过渡）**：先只做「Turnstile + 邀请码/白名单」把注册量控住，等有了域名再开邮箱 OTP。适合内测阶段：不产生发信成本，也不会有送达率问题。

**一个必须提前知道的技术约束**：在没有自有域名时，前端在 `*.github.io`、后端在 `*.workers.dev`，二者属于**不同站点**。跨站 Cookie（`SameSite` 限制 + 第三方 Cookie 拦截）**不可靠**，所以登录态不要依赖 Cookie 会话，应改为 **Authorization: Bearer <token>**（服务端签发、可撤销、有有效期）。等以后前端与接口放在同一个自有域名下，再考虑换成 `HttpOnly` + `Secure` 的同站 Cookie + CSRF 防护。

**验证码本身的实现要点（提案）**

- 发送与校验都在 **Worker 后端**完成：邮箱服务商的 API 密钥只存在于 Worker 机密里，**永不进入前端**；前端只提交邮箱地址与 Turnstile token。
- 验证码必须是**密码学随机**生成的 6 位数字（用 `crypto.getRandomValues` 一类安全随机源），**不允许**用时间戳、自增数或可预测种子。
- 建议初始参数（可配置，不是承诺）：**有效期 5 分钟**、**重发冷却 60 秒**、**同一验证码最多尝试 5 次**（超过即作废，需要重新发送）。
- **存储用带密钥的 HMAC，且必须把验证码本身纳入摘要输入**：`HMAC(secret, 规范化邮箱 | purpose | challengeId | otp)`。这样用户输入的验证码只要不同，摘要就不同（若不含 otp，改输入也不会改变比对值，校验就失去意义）。库里只存摘要 + 元数据（生成时间、尝试次数、状态），**不落库明文验证码**；比对时用 HMAC 摘要做**常量时间比较**。
- **一次性消费**：校验成功即原子标记为已用（Durable Object 或 D1 事务内完成「读取 → 比对 → 标记」），并发请求只能有一个成功；**重发时让旧验证码失效**，避免同时存在多个有效码。
- **发送前限流**：按邮箱地址、按可信 IP（`CF-Connecting-IP` 加盐哈希，不用可伪造的头）、以及**全站每日发送预算**三重限制，**在真正调用邮件服务之前**就拒绝，避免被用来刷你的额度。全站预算超出后应返回可读的「稍后再试」，而不是静默失败。
- **响应不泄露账号是否存在**：无论邮箱是否已注册，都返回同样的通用文案与状态码（防账号枚举）；错误信息不区分「邮箱不存在」与「验证码错误」的细节，只给出可操作的通用提示。
- **日志纪律**：不记录验证码明文、不记录完整邮箱或其它 PII；只记录计数与结果类型（成功/过期/超限），便于排障与风控。

**会话与 Cookie 的现实约束**

- 生产环境建议**同源部署**（前端与 `/api` 同一个域），会话用 **HttpOnly + Secure + SameSite 的 Cookie**，并配套 **CSRF 防护**（双提交 token 或 SameSite=Lax/Strict + 自定义头校验）。
- 现在的形态是静态前端放在 `*.github.io`、Worker 放在 `*.workers.dev`：**跨站 Cookie 在浏览器里不可靠**（第三方 Cookie 受限、SameSite 策略各异），因此**不要**在这个组合上做会话与收费；要收费就必须先确定同源的前端域名。
- 再次强调：**CORS 白名单、发送频率限制、验证码都不是账号鉴权**，它们只是门槛。

**邮件送达的前提条件（上线前必须做）**

- 发信域名必须完成 **SPF / DKIM / DMARC** 的 DNS 记录与验证，否则大量邮件会进垃圾箱或直接被拒。
- 必须做**真实送达测试**（主流邮箱服务商各测一遍，含中文与英文模板），并准备**找回/恢复流程**与**滥用处置流程**（例如封禁恶意发信、处理用户投诉）。
- **不对免费额度或各地区可达性做任何保证**：额度、限速与区域政策都会变化，必须按你自己签约的服务商条款与实测结果来定。

**与计费的关系**

- 后续要收费的 AI 生成必须由**服务端账号 + 信用点账本**来扣减；**不能用 `localStorage` 余额**（客户端可改，等于免费）。
- 账本、幂等与对账的实现要点见第 6 节「尚未实现」列表与第 9 节上线条件。


## 7. 内容与平台许可：公开可看 ≠ 可商用

- **MIT OpenCourseWare**：允许学习使用，但其条款对**商业用途**有限制，且**逐门课程可能有不同的第三方版权**。要商用必须逐条核对每门课的许可声明，不能因为「是 MIT」就默认可以转售或打包。
- **Bilibili 等视频平台**：站内视频的版权归**上传者/权利人**，平台条款不授予你转售或再分发的权利；**嵌入播放**与**商业再分发**是两件事。要商业使用必须获得创作者/权利人许可，并遵守平台条款。
- **不得**转售未获授权的视频、**不得**复制 PPT/课件/游戏素材（本仓库的原创视觉与「不复制上游角色素材」的约定继续有效）。
- 因此：商业化版本里，视频条目应保持**外链引用 + 来源标注**的现状；付费内容应是你自有或已获授权的内容。

## 8. 托管与部署的合规前提

- **GitHub Pages 的可用条款**对「以商业目的运营」的项目有额外限制（例如面向商业客户收费的产品/服务通常需要自备托管）。做店铺/收款之前**必须先核对当时的条款**。
- 生产环境若确需商业用途，**可能需要改用允许商业使用的托管**，例如 **Cloudflare Pages**（配合同一账号下的 Worker）。本仓库目前未做任何商业部署。
- 无论托管在哪，静态前端**无法隐藏共享密钥**：私有部署请叠加 Cloudflare Access 等访问控制；对外商用必须有真正的服务端鉴权与账务。

## 9. 上线前的硬性条件（清单）

1. 真实账单校准：至少用一个真实 Worker + 供应商账号，跑一次**有界**的真实课程（1 次大纲 + N 个知识点），记录真实 token 与费用；本项目历史上只验证到「大纲 + 前 4 个知识点」（约 2k-2.8k 输出 tokens/知识点），更长的课程未验证。
2. 计量与账本：服务端信用点账本 + 冻结/释放 + 幂等扣减 + 对账，且**计费依据只来自服务端**。
3. 支付与退款：确定通道、固定费/最低费、退款政策、发票与税务处理方式。
4. 身份：真正的账号体系（IP 只是粗粒度限流，不是身份）。
5. 内容合规：逐门课、逐条视频核对商业使用许可；确认托管平台的商业条款。
6. 透明度：公开的价格版本号、换算表、上限设置与失败计费说明。
7. 客服与 SLA：明确响应时间、退款条件、无效输出的处理方式。

在这些条件达成之前，**不要上线收款**：现有代码没有收费、没有账号、也没有「免费无限 AI」的承诺。
